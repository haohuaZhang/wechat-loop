Wechat-Loop · 知识库工作台

从「文章仓库」到「内容工作台」

采集已经把数据带回来了，真正缺的不是更多功能，而是让每一篇素材都能被看见、筛选、引用、消费的工作界面。本方案由产品 / 知识库专家、架构师 / 高级工程师、UI-UX 三个角色独立评审后综合而成，并配套一份可交互原型。

版本 v1.0 日期 2026-11-20 参与角色 PM·知识库专家 / 架构师·高工 / UI·UX 配套原型 prototype/kb-workspace.html

00结论摘要

① 五种视图，而不是一张表

素材（列表/卡片）、主题聚类、洞察、集合、保存视图。同一个数据源，按任务切换看法。

② 素材是「可引用的证据」

划线摘录 → 素材篮 → 一键组证据包给写作。写作要的是可引用句，不是全文。

③ 使用状态闭环

未用 / 已引用 / 已成稿三级状态，把 used_as_source 从字段变成进度与提醒。

④ 检索有引用回链

FTS5 全文 + 本地向量混合检索，结果带高亮摘要，点开直达原文段落。

⑤ 零新增部署成本

沿用 JSON 知识库，新增 SQLite 索引文件；不引入服务、不调外部 LLM API。

验收口径

被引用率 ≥ 30%；每次组证据 ≥ 5 条且 100% 带出处；入库到首次引用 ≤ 7 天。

01问题诊断：为什么「简单知识库」感觉没用

现状只有「读」的能力

当前知识库页 = 切换 + 搜索 + 筛选 + 列表 + 详情 + 导出。它能回答「有哪些文章」，但回答不了真正每天出现的问题：

  • 这周竞品发了什么值得拆的？
  • 写这个选题，我能引用哪几段原文？
  • 这个角度我或竞品是不是写过了？
  • 哪些素材囤了三个月一次没用？

四个真实任务（按频率）

日写稿找证据：取 3–5 段可引用原文与出处
日对标追更：竞品近 7 天发了什么、哪篇值得拆
周选题去重：这题写过没，哪个角度还空着
月盘点归档：清理未读、打包导出
诊断结论：采集侧已经有批量、断点续采、重试、去重；知识库侧却停在「只读列表」，两端的投入严重不对等。补齐的不是存储，而是消费链路。

02三角色评审纪要

产品经理 · 知识库专家

先服务「找证据」，再谈管理

  • 对标 Readwise 三栏、NotebookLM 的「来源侧栏 + 引用回链」、飞书多视图。
  • P0 只做读现有字段就能实现的：划线摘录、相关文章、状态筛选。
  • 反对 Notion 式块编辑器与双向链接：用户不在库里写笔记。
  • 反对词云/数据大屏：不回答「哪段能引用」，只放大囤积焦虑。
架构师 · 高级工程师

JSON 继续做主存，SQLite 只做索引

  • 字段只增不改：tags/collections/used_at/quality/hash，幂等迁移 + .bak + 原子替换。
  • FTS5（unicode61 + trigram 兜底子串）+ bm25 权重，索引落在 loop/kb/.index/。
  • 可选本地小向量（bge-small ONNX），装不上降级 hash-ngram，RRF 融合。
  • 一万篇 ≈ 20MB JSON，全量读写 20–50ms 可接受；2 万篇后再迁 SQLite 主存。
  • 写路径 tmp→fsync→os.replace + 单写锁；结果 LRU 60s。
UI / UX 设计师

三栏工作台 + 单一强调色

  • 结构：上下文条 / 左栏集合与视图 / 主区多形态 / 右栏详情可沉浸。
  • 键盘：/ 搜索、j k 切换、x 勾选、Esc 关闭。
  • 筛选可「保存为视图」，让重复操作变成一次点击。
  • 不要渐变玻璃态、不要大留白、不要动效炫技，工具要「安静」。

07技术方案

7.1 数据模型演进（只增字段，幂等迁移）

// articles[id] 追加
{
  "tags": [],              // 用户标签（与自动 keywords 分离）
  "collections": [],       // 所属集合 id
  "used_at": null,         // 首次被引用时间（已引用/已成稿）
  "quality": { "score": 72, "flags": ["thin"] },
  "hash": "md5(url)[:12]"  // 增量索引键，与去重口径一致
}
// 顶层追加
{ "schema": 2, "collections": { "<id>": { "name": "选题池" } },
  "views": [ { "name": "本周新采集", "filter": { "since": "7d" } } ] }

迁移策略：启动时比对 schema → 逐条 setdefault 补默认值（不覆盖已有）→ 写 .bak → 原子替换；可重复执行。

7.2 新增 API（6 个，其余复用）

方法 / 路径要点
GET /api/kb/stats总量、账号/主题分布、未使用篇数、被引用率
POST /api/kb/batch{ids, op: tag|move|delete}，返回影响条数与最新计数
GET|POST /api/kb/collections集合树查询 / 新建 / 重命名
GET|POST /api/kb/views保存视图（筛选快照），供左栏一键入口
GET /api/kb/search?q&mode=kw|vec|hybrid返回 hits（score + 高亮摘要片段），支持游标分页
GET /api/kb/article/<id>（扩展）追加 similar[]、duplicateOf

7.3 检索：FTS5 为主，向量可选

  • 分词：FTS5 unicode61 字级分词 + trigram 列兜底中文子串。
  • 打分：bm25，权重 title > keywords > body；结果返回命中片段与偏移，前端做高亮。
  • 向量（P2）：离线 bge-small ONNX 256 维，1 万篇 ≈ 10MB 常驻；装不上自动降级 hash-ngram，并用 RRF 融合两路结果。
  • 索引生命周期：loop/kb/.index/<kb>.db；按 hash 增量 upsert；写入标脏后台重建；启动用 count+mtime 校验，损坏即重建。

7.4 性能与一致性

  • 元数据常驻内存；正文懒读并按 mtime 缓存；列表游标分页 limit ≤ 200。
  • 写路径 tmp → fsync → os.replace + 单写锁，避免半写损坏。
  • 查询结果 LRU 60s，写后失效；10k 篇 JSON ≈ 20MB，全量保存 20–50ms 可接受。
  • 超过 2 万篇时再考虑「元数据 + 分片」或迁移 SQLite 主存 —— 当前阶段不做。

08分期路线

P0 · 第一周

  • 字段追加 + 幂等迁移 + 原子写
  • 批量打标签 / 移动 / 删除
  • /api/kb/stats + 洞察页
  • FTS5 索引 + /search + 高亮

P1 · 随后

  • 划线摘录 + 素材篮 + 组证据包
  • 集合树 + 保存视图
  • 主题聚类 + 覆盖度
  • 相似 / 重复检测

P2 · 有余力

  • 本地向量 + RRF 融合
  • 发布回流自动标记引用
  • 质量评分与「薄文」提示
  • 增量导出（按筛选/集合）

09指标与验收

≥ 30%被引用率：used_as_source / 总篇数（当前 ≈ 0）
≥ 5 条每次组证据的引用条数，且 100% 带出处 url
≤ 7 天入库 → 首次被引用的中位数时长
当前只有 2 篇真实素材，所有交互都用演示数据在原型中评审；落地时先用采集脚本灌入 50–200 篇真实文章回归，再进入 P0 开发。

10明确不做

✕ 块编辑器 / 双向链接

用户不在知识库里手写笔记，维护成本会压垮价值。

✕ 词云 / 数据大屏

不回答「哪段能引用」，只放大囤积焦虑。

✕ 无限信息流

没有边界的浏览会稀释任务感；用集合与视图收口。
